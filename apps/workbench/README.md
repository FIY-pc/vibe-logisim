# workbench

The window. React 19 + Zustand, one `Workbench` per mount (`app/createWorkbench.ts`): eight stores, four action groups, one host subscription. Every mutation of circuit state goes to the host; the window keeps only view state (selection, tool, viewport, open panels, drafts) and the last snapshot it was given.

## Owns

- `app/`: composition and lifecycle. `createWorkbench` builds `Stores{notices, settings, shell, conversation, documents, files, editor, simulation}` and `Actions{workspace, editor, simulation, navigation}`; `start.ts` subscribes; `router.ts` applies host events (`simulation`, `resync`, `warning`, connection loss); `keyboard.ts` the shortcut dispatcher; `view.ts` the `View{doc, circuit, instance, scope}` every component reads (`instance`: the subcircuit instance path shown, empty for the circuit itself); `provider.tsx` the React context; `hooks.ts` selectors; `reaction.ts` store-to-store reactions.
- `shared/`: `transport.ts` (`command(request)`: Tauri `invoke("command")` on desktop, `POST /api/command` in the browser; `openPath`/`savePath` file dialogs), `events.ts` (`subscribeEvents`: the page's Tauri `events` channel or SSE), `host-error.ts`, `notices.ts`, `settings.ts`, `shortcuts.ts` (the key table, user-editable), small controls (`DecisionDialog`, `IconButton`, `PropertyField`, `TextPrompt`, `Select` — the only drop-down list, `Checkbox`, `useAutoSize` for growing text areas). Every layer is drawn by the app, never by the platform or its theme: `Menu`/`MenuItem` (button menus, the "···" ones included) and `ContextMenu` (right-click) on Radix menus, `Select` and `Checkbox` on Radix, `Dialog.tsx` (`DialogFrame`: controlled Radix Themes modal with title, close, optional footer and focus return; `DialogBody`: scrollable content, or `scroll={false}` for independent viewports; `DialogFooter`: persistent actions; `useModal` remains only while native callers migrate), `layer.ts` (portal container inside the open dialog, focus return), and `Tooltips` — one hint layer for `data-tip` (`tip(text, shortcut)`, `fullText(text)` for labels cut short); native `title` is not used. Commands that open a dialog or a file picker end with "…", commands that act at once do not.
- `shell/`: frame and chrome: `WorkspaceLayout`, `Titlebar`, `Rail` (left tool rail), `Aside` (right column: chat, files, inspector…), `Notices`, `DecisionRegion` (blocking questions), `Feedback*`, `ShortcutSettings*`, `store.ts` (which panels are open, pending host calls).
- `workspace/`: the folder and open files: `documents.ts` (open documents, active id, workspace refresh), `filesStore.ts` + `Files.tsx` (folder tree, file history with undo, imports), `FilePreview` + `reader/` (persistent material tabs, split view, PDF.js Viewer, image regions, Markdown/text, and citation navigation), `ProjectInfo` (summary, export), `Welcome`, `FolderPrompt`, `NewFilePrompt`, `SourceNotices` (file changed on disk / missing), `actions.ts`.
- `editor/`: the canvas and editing. The window composes the editor picture itself (`docs/rendering.md`): `symbols.ts` (the recorded pictures of the kinds of components, cached per document by library, name and attributes; `useSymbols` asks the host's `symbols` only for the kinds the document has not drawn yet; the width-conflict wires come with the edit, undo and redo answers (`DocumentChange.widthErrors`, kept per circuit by `recordWidthErrors`), and a circuit shown before any answer reported them (just opened or re-read) gets them from one `symbols`; `keepSymbols`, which `actions.ts`'s `watchSymbols` calls with the open documents, forgets closed ones), `paint.ts` (`program` compiles a picture's ops, `buildScene` lays out parts, wires, junctions, bounds and ports, `paintFrame` paints one frame, strokes placed on the pixels Java2D puts them; during a run it paints the run's wires, junctions and components instead, `Frame.live`), `CanvasPicture.tsx` (the `<canvas>` under the SVG layer, painted at the next animation frame), `geometry.ts` (hit testing, box selection and fitting from the recorded bounds), `useConnections.ts` (`connections`: only the nets of the selected components and wires and of a traced click, each seed read once per revision, only while connections or a traced signal are shown), `usePlacementQueue.ts` (placement clicks committed in order, each ghost kept where it was clicked until the document has it), `useMovePreview.ts` (`movePreview` while dragging: the wires Logisim's move gesture would take out and add, one request at a time, which the drag never waits for). `Canvas.tsx` is the interaction (tools, pointer and keys, dragging, wiring, commits, marks on the SVG layer) and assembles the frame it paints. Around it: `store.ts` (tool, selection, viewport, placement), `actions.ts` (edit, undo, redo, move, delete, attributes through host ops), `usePlacement`, `EditorToolbar`, `Inspector` + `PlacementInspector` (attributes via `properties`/`template`), `PaletteRegion` (`catalog`), `Connections*`/`connectivity.ts` (signal tracing on the nets read with `connections`; every record carries the document's ids, so a selection and its connections match by id), `CircuitList`/`CircuitActions`/`CircuitPrompts`/`Breadcrumbs`/`navigation.ts` (subcircuit navigation), `FindDialog`, `InterfaceEditor` (subcircuit pins and symbol), `SourceDialog`, `arrange.ts` + `arrange-worker.ts` (`packages/arranger` in a module worker for the user's own "整理" action), `symbol-geometry.ts` (the interface editor's symbol shapes), `componentLabels.ts`.
- `simulation/`: `store.ts` (what the events say: the run, the shown frame's circuit, instance path and clock, components, the picture `paint`, the waveform, the memory page, how the last run ended; plus inputs waiting for their frame by `commandSequence`; `live(state, view)` is whether the canvas shows the run), `actions.ts` (`simulationStart`/`Command`/`Navigate`/`Stop`; `onEvent` is the only writer of run state), `simulation.ts`, `simulationInputs.ts` (poke, input values, buttons), `SimulationControls`/`SimulationDock`/`SimulationTransportRegion`/`SimulationMenuRegion`, `InstanceBar`, `MemoryPanel`, `Waveform`, `Observations` (kept observations), `SimulationAlerts`, `CaptureNotice`.
- `conversation/`: `Chat.tsx` (binding to the folder's conversation, sending, stopping, replaying `agent` events by sequence), `turns.ts` (splits the messages into one segment per question, the summary line of a finished turn), `Turn.tsx` (one turn: live steps, the folded summary, the end line, the files card with undo), `ConversationContent` (markdown, copy, conversation picker), `ConversationList` (React Virtuoso scrolling and turn virtualization), `TurnExpansion` (conversation-scoped disclosure state across recycled rows), `ChatReferences` + `references.ts`/`conversationReferences.ts` (attached files and observations), `ModelPicker`, `ProviderSettings` (services, keys, probe), `store.ts`.
- `history/`: `DocumentHistory` (per-document history list), `HistoryReview` (review of one entry with before/after render and read-only CodeMirror XML comparison), `ChangesRegion`.
- `generated/`: TypeScript copies of the host types. Never edited by hand; `npm run contracts`.
- `src-tauri/`: `main.rs` (creates `Host`, exposes the `command` invoke and the per-page `events` channel, shuts the host down on exit), `installation_check.rs` (bundled runtimes present), `tauri.conf.json`.

## Does not own

Any rule about documents, saving, history, simulation lifetime or AI scope. If the window has to check something to stay correct, that check belongs in the host; the window only displays the host's answer.

## How data flows

- Read: a component calls `useWorkbench()` → store state. Stores are filled from host results (`status`, `read`…) by the action modules; run state only from `simulation` events. The canvas's own reads (`symbols`, and `connections` while connections are shown) stay in its hooks; what `connections` answered is copied to `editor.store` (`canvasObservation`) for the inspector.
- Write: an action builds `{op, ...}` → `command()` → host → the result replaces the relevant store slice. Edit, undo and redo results carry `change` (what changed since the revision they were sent for, only the changed circuits), `selection` and `title`; `documents.applyChange` applies it to the open document, or reads the workspace again when that document is no longer at the change's base revision. The canvas shows the host's revision. A committed wire, delete or move draws its own result (the new wire, the objects hidden or displaced, the move's rerouting from `movePreview`) from the next frame until that revision arrives, and placement ghosts stay where they were clicked; nothing else is predicted (wire repair, merged wires and changed kinds come with the answer). A drag moves the selection with the pointer and sends nothing it waits for; release is one `edit` move, which Logisim's move gesture resolves (an end dropped onto a wire connects). Shift while dragging moves without keeping connections, as in Logisim. Where the move would leave an end unconnected, red dots mark the end's old and new place. A picture or connection read the host refuses as stale (`STALE_REVISION`: another revision exists) re-reads the workspace instead of showing an error; only a refused edit reports it.
- Push: `router.ts` → `simulation` events into `simulation.store` (each subscription, a reloaded page's too, starts with the run's whole state); `resync` → re-read the workspace; `change` → `documents.applyChange` (the AI's edits, undos and redos, a document reloaded from disk, any document another request changed; the window's own change comes in its reply); `source` → `documents.setSourceStatus`; `workspace` → `documents.setWorkspace` (the host opened, closed or activated a document outside a command of this window: it adds and removes those documents and reads only the newly listed one); `warning` → notice. The window polls nothing. `agent` events go to `Chat.tsx`, which owns the sequence gap check: it loads the conversation with `history` when it binds, switches conversation or misses events, replays newer buffered events after it, and otherwise reads the state alone with `status`; the sidecar relays no document changes.
- Shortcuts: `shared/shortcuts.ts` table (1 选择, 2 布线, 3 操作输入, 4 平移, A 元件库, Ctrl+K 时钟, Ctrl+T 一步, Ctrl+Z 撤销, Ctrl+S 保存, Ctrl+, 快捷键) → `app/keyboard.ts` → actions.

## Material reading

PDFs use Mozilla's complete generic viewer, pinned by version and SHA-256 in `config/pdf-viewer.json`. Vite downloads it once into `.workbench-cache` and includes the viewer, fonts, locales and worker in the offline application. `reader/pdf-bridge.mjs` connects project bytes, saved reading position and citations; the upstream viewer owns search, selection, page navigation and zoom.

PPTX files use the lazy-loaded `pptx-react-viewer` canvas and OOXML parser, pinned in the npm lockfile. Slides render locally without Office, LibreOffice or a document upload. The workspace provides page navigation, zoom, saved reading position and page quotations (text plus a PNG). With the slide canvas focused, arrows, PageUp/PageDown and Space/Shift+Space turn pages; Home/End jump to the ends. Hovering either page edge reveals a larger previous/next button. A wheel gesture turns one page; zoomed pages scroll first and require a fresh gesture at the edge to turn. Ctrl/Meta+wheel retains the renderer's zoom. These inputs stay inside the canvas and leave text selection, links and form controls alone. Whole-file quotations extract slide text through the same parser. The viewer runs without editing, recovery autosave, remote fonts or linked external media. Embedded fonts and EMF/WMF images are handled by the upstream renderer; layout may differ when fonts are missing or a PowerPoint effect is unsupported. This is a static reading view, not a slideshow player or editor. Legacy `.ppt` is not enabled.

Material tabs stay open beside the circuit or expand into the editor area. Quotes retain the file revision, page and normalized region; conversation links reopen the source, or show the saved quotation if the source is gone. The runtime's `read_material` tool reads and searches the original PDF independently of the visible page, and renders diagrams or pages without text. It does not perform OCR.

`read_material` currently handles PDF and images, not PPTX. PPTX page quotations carry the captured image and text directly into the conversation; they do not require that tool.

### Export conversations

Open the conversation title/history picker and choose **导出会话…** (also available in **对话操作**). Select any number of current-workspace conversations, including archived ones, or use **全选 / 取消全选**. The ZIP contains only checked conversations; each has a readable `conversation.md` and a complete `conversation.json`. Duplicate titles use distinct numbered directories. Content comes from the sidecar's full history and transcript, including complete tool arguments/results and available thinking, regardless of folding or virtualization. In-progress conversations are snapshots of the content available when exported. Account/profile files and service credentials are not included; conversation content itself is preserved.

`node scripts/workbench/verify-conversation-export.mts` runs the actual browser, Rust host and sidecar with synthetic data. Build the host first with `cargo build -p vibe-workbench-host`. It checks the history entry, multi-selection, ZIP download/content and the native file-writing path, using independent temporary ports/state and no model calls. `VIBE_EXPORT_EVIDENCE` optionally keeps the browser screenshot and downloaded ZIP.

For manual checks, create an empty workspace folder and run:

```sh
mkdir -p /tmp/export-fixture-workspace
node scripts/workbench/fixtures/conversation-export.mts /tmp/export-fixture-state /tmp/export-fixture-workspace
```

The state directory must not already exist. Start an independent preview host with `VIBE_WORKBENCH_STATE=/tmp/export-fixture-state`, then open `/tmp/export-fixture-workspace`. The dataset has 24 conversations, a 600-turn history, duplicate titles, archived history, available thinking and long failed-tool output. No personal conversations or credentials are used.

### Conversation list verification

`npm run test:conversation-browser` runs the real `Chat` in Chromium against a synthetic 600-turn event stream, on a temporary local port. It checks bounded mounted rows, nested disclosures after recycling, reference context, streaming follow and reading position, tab visibility, conversation switching and remount. No host or model is used. Install Chrome, set `BROWSER_PATH` to a Chromium executable, or run `npx playwright install chromium` and set `BROWSER_CHANNEL=chromium`. `CONVERSATION_SCREENSHOT` optionally saves the final view. The regular UI suite uses Virtuoso's official mock measurements for domain/lifecycle assertions; it does not prove scroll geometry.

Virtualization is per user turn and preserves the existing message projection. A single very large expanded turn or Markdown answer is still rendered as one item. Conversation switching opens the selected history at its latest turn; temporary tab hiding keeps the current reading position. Disclosure choices survive offscreen recycling within that conversation, and a newly completed turn still folds its process as before.

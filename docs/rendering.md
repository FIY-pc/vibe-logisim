# 画布渲染方向

## 当前事实

当前画面有三层职责：Logisim 的 Java `Circuit.draw(Graphics2D)` 产生权威电路图，浏览器 SVG 层承载选中、端口、导线和放置预览，仿真运行时再把原生 PNG 帧放到画面层。平移和缩放只改变 SVG `viewBox`；视野细化才会请求新的原生 PNG。

这条链路保留了课程 Logisim 的元件外观和运行语义，但静态图的清晰度受位图分辨率约束。原生局部绘图目前限制了单张图片的像素尺寸和面积，长电路在一次请求覆盖很大世界范围时会主动降低分辨率；这正是极端长画布放大后发糊的主要候选原因。

真实 Electron 基准使用课程流水线电路 `◇气泡流水线`（1188 个元件、131 段导线）测得：画布约 4823 个 DOM 节点，拖动期间没有长任务，动画回调中位约 16.7ms；释放拖动后等待高清细化的中位约 94.5ms，P95 约 137.8ms。这个结果说明浏览器交互合成不是第一瓶颈，原生重绘、编码、传输和交接才是下一步应拆开的路径。脚本的测量不等同于 GPU 呈现时间，也不代表所有显示器和电路。

运行基准：

```sh
node scripts/bench/rendering.cjs /path/to/circuit.circ "电路名"
```

脚本只在临时工作区打开真实 Electron，通过鼠标平移和缩放记录视野请求、细化等待、长任务和源文件摘要；不启动 Codex、不写回原电路。

## 矢量实验的结论

让 Batik 记录同一个 Logisim `Graphics2D` 调用可以生成 SVG，因此小电路可以保留原生外观并获得无损缩放。全加器实验中，SVG 约 112KB，原生 PNG 约 90KB；SVG 记录约 5–8ms，PNG 编码约 21ms。

大流水线实验中，整张 SVG 约 6.8MB，记录约 180ms、序列化约 35ms；同一电路的局部 PNG 约 100KB。这说明全量 SVG 适合小电路或导出，不适合作为所有大电路的默认画面。未经筛选的矢量输出已经在本地实验中验证过，但尚未接入产品主链路。

## 目标架构

渲染器应按“场景、视图、交互、运行”分层：

1. Logisim 继续是元件绘制和课程兼容性的唯一权威。
2. 静态画面使用按视野切分的高分辨率瓦片，并以电路版本、视野和像素密度作为缓存键。瓦片大小固定在可控范围内，长电路不会因为一张图太长而整体降采样。
3. 小电路可以选择矢量视图；选择依据是元件数量、预计 SVG 大小和生成耗时，而不是盲目全量使用 SVG。
4. 交互对象保持独立层，不能因为重绘静态图而丢失选择、连线预览或临时元件。
5. 仿真值保持独立的运行层；静态层不因每次输入变化而重新绘制。
6. 每个视图请求都要能取消、合并和丢弃过期结果，避免用户连续操作时旧图覆盖新图。

下一步优先实现静态 PNG 瓦片和可见区域缓存，然后用同一基准比较清晰度、首帧和细化等待。矢量层作为小电路的可选路径保留。只有在测量显示合成或交互层成为瓶颈后，才评估 Rust；Rust 直接重写 Logisim 元件绘制会失去课程库兼容性，当前证据不足以支持这个代价。

## Rust 的边界

Rust 适合未来承担独立的瓦片调度、缓存和 GPU 合成服务，前提是基准证明 Python/Java/浏览器交接仍是瓶颈。它不应首先承担 Logisim 元件绘制和 `.circ` 语义重写：那会复制现有 Java 运行时，扩大兼容性风险，却不能自动解决位图分辨率和视图缓存问题。

# 实际案例：从 HUST 课设框架到七个 CPU 入口

这份案例记录 Vibe Logisim 内置 AI 完成的一套数字电路课设。电路在 HUST 课程 Logisim 运行时中实现、仿真和渲染，产物为可继续编辑的 `.circ` 文件。

## 做出了什么

| 电路入口 | 主要内容 |
| --- | --- |
| 单周期 CPU | 基础指令、访存、分支、显示与暂停 / Go |
| 理想五段流水 | IF、ID、EX、MEM、WB 五段与真实流水寄存器；程序使用软件调度 |
| 气泡流水 | 数据相关停顿、分支冲刷、WB→ID 同拍写穿 |
| 前递流水 | 操作数前递、load-use 停顿与控制冒险处理 |
| 单级中断 | 优先级、进入服务程序、保存与恢复返回地址 |
| 多级中断 | 硬件 EPC 栈、三级嵌套与逐层返回 |
| 流水中断 | 流水控制与中断响应结合，另做本地验证 |

指定的 CCAB 编号为 **2434：SRL、XOR、LH、BGEU**。原课设面板、按钮及入口接口保留；数据通路与控制逻辑按功能组织。

## 人与 AI 分别做了什么

内置模型使用自定义提供商的 `gpt-6-astra`，思考深度 high。它阅读材料，使用脚本、电路工具、原生仿真与局部图面检查，实现电路、组织图面并修复错误。功能分组与布局辅助工具是可选手段；这份课设的实现也包含模型直接编写的电路生成脚本。

用户确定目标与扩展指令，评价图面并补充平台要求。外层协助整理材料、把平台反例交给内置模型、独立核验功能与实际自测结果，没有手改 CPU 实现。

## 怎样达到最终结果

先完成理想流水首版，再继续扩展整套课设。过程中出现提供商的图像数量上限，改用新对话接续已保存工程；反馈中断按钮未接通和扩展指令缺失后继续修正。因此，这不是整套课设一次 zero-shot 完成的记录。

进入平台自测后，进一步发现演示程序与提交程序不同，以及停机 PC、气泡周期、冲刷和中断采样时点的差异。内置模型根据这些实际反例修复行为，并为各关保存专用提交文件。

最后两关还暴露了中断服务程序的地址差异：实际 PC 为 `0x00AC`，平台期望 `0x30AC`。模型将服务程序真正重定位到高地址并同步向量，随后重新自测通过，没有通过修改显示值来掩盖行为差异。

## 实际验证到了哪里

截至 **2026-10-08**，选定的第 1、2、3、4、7、8 关，六份最终电路均已逐份粘贴到平台、读回核对文件摘要，再实际运行自测，均无错误输出。这里使用的是本次新运行的记录，未沿用历史成绩，**没有提交正式平台评测**。第 5、6、9 关为其他实现路线，不计入这次结果。

另外对七个入口做了本地指令、访存、分支、显示和暂停 / Go 检查，并核验三种中断入口及嵌套返回。最终工程的 22 个原生视图可正常加载，无无效线束。图面质量由实际图面与人类反馈判断，不由功能测试结果换算得出。

## 怎样用在自己的任务上

准备原始工程、实际依赖和验收输入，说明要保留的面板与接口。先读主数据流、运行关键程序，再提供具体反馈，例如一根绕远的输出线、一个难以追踪的字段，或某一拍的预期与实际差异。让 AI 根据反馈继续修图和修功能，并复查之前已经正确的行为。

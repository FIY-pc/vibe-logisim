# agent-runtime

The AI turn. A Node sidecar the host spawns once per application run; it holds the user's model services, the per-folder conversations, and the tools the model uses. It owns no circuit state: every tool call is a host request on the live document, so the user sees edits appear in the editor as they happen and can undo them with the same history as their own edits.

## Owns

- `worker.mts`: process entry. Reads `{kind:"request", id, method, args}` lines on stdin, answers `{kind:"result"}`, pushes `{kind:"event"}`, and calls the host with `{kind:"host", id, request}` answered by `{kind:"hostResult"}`. Sends `{kind:"ready"}` after start. Argument: the state directory.
- `protocol/`: the shapes shared with the host and the window: `host.mts` (`HostClient`, `HostStatus` (the host's `status {summary: true}`), `HostFolder`, `FolderChange`, `isHostError`), `messages.mts` (`RuntimeEvent` union: status, history, message, user-message, assistant-started/-delta/-completed, activity, conversations-changed, runtime-error, turn-started, turn-completed, files-changed), `types.mts`.
- `models/`: `chatgpt.mts` (native OAuth, validated identity, account-specific model inventory, serialized token refresh and logout), `chatgpt-responses.mts` (ChatGPT plan Responses payload and bearer transport), `services.mts` (`ServiceStore` in `<state>/profile`: custom OpenAI-compatible / Anthropic / Responses endpoints, keys kept out of logs; `modelFor`, `transport`, `APIS`), `catalog.mts` + `catalog.snapshot.json` (public model metadata, `npm run catalog:update`), `probe.mts` (`discoverModels`; the connection test is `TurnRunner.probeService`), `selection.mts` (`selectionFor`, `configurationIssue`, `recoverHistory`), `validate.mts`, `sdk.mts`/`sdk-loader.mts` (pi-ai streaming).
- `network/`: `system-proxy.mts` (`resolveSystemProxy`: Windows and env proxies) and `fetch.mts` (`networkFetch`, `systemProxy`, `closeNetwork`). All model traffic goes through `networkFetch` on the route `resolveSystemProxy` picked.
- `conversations/`: `store.mts` (`ConversationStore`, `<state>/conversations.json`, keyed by folder id; read once, then kept in memory, and every save rewrites the file), `references.mts` (user-attached files and observations: `storeReference`, `readReferences`, `referenceSummary`), `types.mts`, `reference-types.ts` (shared with the window).
- `turn/`: `instructions.mts` (system prompt: who the model is, the folder and file model, ids and evidence, writing .circ XML yourself, what counts as context), `runner.mts` (`TurnRunner`: one turn at a time, interrupt, folder checkpoint before and after, event stream; a running turn saves its conversation at most every 500 ms, its start and end save at once), `activity.mts` (`toolActivity`: the Chinese one-liners the window shows per tool call), `context-budget.mts` (`ConversationContext`: Pi compaction over a persistent transcript; requests use a summary and recent messages while the full log and edit checkpoints remain intact).
- `tools/`: 16 tools (`schemas.mts`, `TOOL_SPECS`): open_circuit create_circuit define_circuit inspect_circuit render_circuit describe_component place_component set_attributes connect move_components delete_objects arrange_circuit simulate_circuit trace_circuit undo_edit read_observation, plus `files.mts` (read_file, write_file, list_files, exec_command inside the folder; references read-only). `context.mts` (`ToolContext`: keeps no document, only which id is open at which path. `resolveDocument(path?)` asks the host for the document's fields (`read {id, circuits: []}`, or `open` when the path is not open yet), so a tool call is that read plus the request that does its work: an edit, an observation, a render; `open_circuit` reads every definition to report their sizes; `edit` sends one `batch` per call (its wire, place, delete and attribute edits, and its moves) with the revision it read, so each tool call is one undo step and a refused move moves nothing; the host broadcasts the change to the window). A `place_component` or `connect` addition without `library` costs one `catalog` request; `move_components` with positions computes each offset from the id, which is the anchor; `connect` with connections observes before routing and after drawing. `index.mts` assembles `circuitTools({context, vision})`.
- `tools/wiring.mts`: the router behind `connect`. `new Router(circuitView)` paints the observed definition on the 10 px grid (bodies, port and wire-end joints, wire interiors per net, the directions each port leaves its body); `route(from, to)` is A* from anywhere on the first net (its ports and every wire point) to anywhere on the second, with a cost per bend (4), per wire crossing (3) and per body cell (25, straight only, for ports boxed in by a tunnel or a neighbour); `commit(points)` adds a drawn route to its net so later routes of the same call branch off it. It never ends or bends on another net, never runs along a wire, and meets ports head-on. `connect` then observes the result and checks that exactly the requested nets were joined (`ROUTE_CHANGED_NETS` takes the wires back otherwise).
- `circuit-knowledge/`: Markdown the model can read (`index.md`, `digital-design.md`, `java-runtime.md`, `arrangement.md`: facts only, no procedure). Bundled read-only with the product; the prompt names the folder and nothing else.

## Does not own

Rendering, document identity, saving, history (host); layout algorithms (`packages/arranger`, called through `tools/layout.mts` in a worker thread); UI state.

Events reach the window as host events on topic `agent`, in order, with a sequence number; the host adds the cursor of the newest event to `status` and `history` (`eventCursor`). The window loads the conversation once with `history` (binding, switching conversations, after missing events) and replays the buffered events newer than its cursor; after that, events carry every change: `message` adds or replaces one entry by id (a turn record when it starts and ends), `history` replaces the whole list (resume, resend cut), `status` carries the state only. Each turn's record (`type: "turn"`) carries `status`, `error` (Chinese; `已停止` after a stop), `startedAt`, `elapsedMs` and `change` (the folder change it made, `undone` once undone). `transmission` is the retry notice while the model service is busy, null otherwise. The sidecar sends no document events: the host broadcasts every change (`change` topic) and the window applies it.

Host ops the tools use: status (`summary: true`) read open new edit undo observe observeXml template catalog render simulate trace folderCreate folderCheckpoint observationList observationGet observationImage. An edit's reply carries `{change, revision, noop, title, circuit, changedCircuits, selection}` plus `widthErrors` on the change and the host's `saveError`/`historyWarning`/`referenceWarning`; the tool answers with the same identity, the placed and new-wire ids, the width conflicts and those notes, so one call tells the model everything about its edit. Each turn starts with `folderCheckpoint {title: "文件改动"}` and ends with another titled after the question, so the user's file history shows one undoable entry per turn (`files-changed` event).

## Invariants

- The conversation scope is the folder id from host `status`; without an open folder `ask` fails with `请先打开工作文件夹`.
- A tool never caches a view across revisions: `ToolContext.edit` sends the revision it read and surfaces `StaleRevision` to the model as an error it can retry after re-reading.
- The tools work on the file as it is: the host checks each open document's file before every document and folder request (`crates/workbench-host/src/documents/files.rs`), so a `write_file` or shell command is visible to the next tool call and to the window without the sidecar doing anything. A document with unsaved changes is never overwritten.
- Component ids are positions (`c<x>_<y>`); the model is told so in the instructions and must not expect ids to survive a move.
- Model-facing errors are `CircuitToolError` with the host's Chinese message and `code`; never a stack trace.
- ChatGPT login uses the documented dynamic public-client flow with PKCE, state and nonce. The callback listens only on `127.0.0.1`, expires after five minutes, and accepts each attempt once. ID tokens are verified against discovery/JWKS before changing accounts. Account registrations remain distinct by issued client ID and verified subject; signing out clears tokens while preserving registration and host identity.
- ChatGPT credentials live in `<state>/profile/chatgpt-accounts.json`, written atomically with user-only permissions on Unix. The host's OS state-directory lock guarantees one sidecar writer; concurrent token refreshes share a promise. Tokens are resolved per inference request and never enter status, conversations or browser storage. API service records remain separate. A failed remote revocation still clears local tokens and reports that remote disconnection was not confirmed.
- ChatGPT inference uses `/v1/responses` with streaming, `store:false`, client-managed history and namespaced local tools. It preserves the existing Pi agent and all circuit tools. No implicit API billing fallback occurs. Account model lists come from `/v1/models`; usage-limit failures stop retries and retain the usage-settings link.
- Credentials: keys live only in `<state>/profile`; nothing in this package logs request headers or writes keys elsewhere.

## ChatGPT methods

`loginChatGPT {id?, consent?}` starts a loopback listener and returns `{attemptId, url}`. The UI opens the URL in the system browser. `chatGPTLoginStatus {attemptId}` returns pending/complete/error/cancelled, with a service ID on success. `cancelChatGPTLogin {attemptId}` closes the listener. `logoutChatGPT {id}` revokes the renewable session and clears local tokens. Account details and usage management live in AI settings. Existing bind/default/model methods work with both account and API services.

Protocol reference: [registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

## Status

ChatGPT authentication and a streamed circuit-tool loop are covered by a local OAuth/JWKS/Responses fixture (`scripts/workbench/chatgpt-check.mts`), including images, refresh, restart, logout and usage failures. Real account login and subscription inference still need hands-on verification; these checks spend no model credits.

Works end to end: a real-model turn on a large project (rename a pin label in a subcircuit) went through this runner, and `npm run test:native` runs a scripted turn through the real sidecar, tools and host. With the scripted model, a full adder from an empty folder (create, place, connect, simulate, arrange, render) takes about 0.5 s; a place, connect, move and arrange turn on a 700-component definition of a 1 MB file about 4 s, half of it `arrange_circuit`.

## Generation limits

`models/generation.mts` resolves output capacity from the service's optional `maxOutput` override, then the model catalog. There is no application-wide 8K cap. With unknown OpenAI-compatible models, request token fields are omitted so the endpoint chooses its default; this is not a promise of unlimited output. Anthropic Messages requires a numeric ceiling: if metadata is absent, configuration asks for `maxOutput` in advanced settings instead of guessing. Pi still fits a known output ceiling into the remaining model context. ChatGPT plan requests omit the unsupported output-limit field.

Context configuration accepts the supplied positive integer without silently clamping it to 32K–2M. Turns have no application-level duration or tool-step ceiling. The 64-token / 30-second connection probe is separate from normal generation. HTTP startup, retry, document-operation, pagination and process-memory bounds serve their respective operations rather than limiting an entire AI task.

On Linux and Windows, `exec_command.timeout` defaults to 120 seconds, accepts longer durations, and accepts `0` to run until completion or user cancellation. Linux uses a systemd sandbox. Windows runs PowerShell 5.1 without a profile, in the open project folder; its PATH contains the bundled Node.js, bundled Java when available, and Windows tools. No separate shell, Python or Node installation is required. Commands are passed through a temporary UTF-8 script, so non-ASCII text and long scripts do not depend on console encoding or command-line length. Output retains the last 64,000 characters and reports truncation on Windows.

Windows commands use the current user's filesystem permissions: setting the working directory is not filesystem isolation. The environment is built from OS essentials and product paths, without inheriting provider keys, account state, proxy credentials, `NODE_OPTIONS`, or user profiles. A Windows Job Object owns PowerShell and its ordinary descendants, with the same 6 GiB / 512-process resource limits as Linux. Completion, cancellation and timeout end those descendants as well. This is process/resource management, not a security sandbox; it does not confine filesystem access or broker-launched processes. Model instructions describe the actual boundary.

`node scripts/workbench/windows-command-check.mts` exercises the real Windows tool with Unicode paths and XML, long commands, exit codes, environment isolation, cancellation/timeout, and descendant cleanup. It runs in Windows regression CI; it skips on other platforms. Packaging also runs it with the relocated bundled Node and runtime paths.

## Context management

The runner uses Pi 1.5's `findCutPoint`, `generateSummaryWithUsage` and context estimator. Before each model request, including requests within a long tool turn, it checks usage against the context window with reserved headroom (at least 16,384 tokens where the window permits, otherwise a proportional reserve). It summarizes older complete tool batches and retains about 20,000 recent tokens, scaled down for smaller windows. Oversized tool output is summarized in chunks. The summary preserves goals, constraints, decisions, file/circuit identities, changes, verification results and pending work. It uses the same selected service and its normal output capacity; summary requests cannot execute tools.

`ConversationRecord.compactions` stores summary boundaries into the unchanged raw transcript. The model's projection changes only at a compaction boundary; subsequent requests reuse that prefix. Reloading restores it. Editing an earlier message discards checkpoints that refer to superseded work. Failure or cancellation leaves the old projection intact. A provider context-overflow response triggers one forced compaction and continuation in the same turn.

Status exposes `contextUsage {tokens, contextWindow, source, compactAt, status, compactions}`. Pi uses the latest valid provider usage plus estimated new messages, falling back to estimation when no valid usage exists. The composer ring turns yellow at 75%; values and compaction state appear on hover or focus. Arrangement workers run until completion or user cancellation, with no fixed 60-second deadline.
